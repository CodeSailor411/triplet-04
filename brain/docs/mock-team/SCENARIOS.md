# Five primary mock scenarios

Source: CIVIS 4 October incident/response table. Five scenarios are selected for this checkpoint; the source has eight incident rows. Road accident, low water and fire are deferred. Conditional secondary responses are not part of the first implementation. IDs below name workflows, not test variants.

| ID / owner | Input and detector boundary | Primary response | Required proof |
| --- | --- | --- | --- |
| S01 / Yassine | congestion_index in percent at two distinct consecutive ticks on a Traffic node; mock threshold only | R1 set_signal_plan using advertised plan/carrier | Approved request commits once; low/null/duplicate ticks do not cause an extra action |
| S02 / Meriem | water_level in cm with local datum; high-water candidate, not proof of leak | R3 set_valve_position only with supplied topology and required safe preview | Safe fixture preview permits exact approved valve request; missing/unsafe preview blocks with zero actuate |
| S03 / Elyes | load_kw/voltage_v only; no agreed live overload threshold or outage flag | Alert/blocked with explicit evidence limitations; no grid switching in reduced version | Insufficient fault/topology/preview is recorded; low load never becomes an asserted outage |
| S04 / Elyes | pm25 in ug/m3 sustained on two distinct ticks; fixture threshold only | Air-quality alert | Alert and evidence saved; zero actuator/dispatch calls without independent emergency evidence |
| S05 / Maram | emergency_calls channel medical at reported location; units_free ambulance availability | R2 dispatch ambulance with carrier target and separate destination | Available/approved dispatch commits once; zero availability/denial produces no dispatch |

Incident kinds for these modules are congestion, flood, power_fault, air_pollution and medical. If Power cannot support a fault candidate, return observations plus a warning and let the shared core record the unsupported-evidence outcome. Do not invent a fault flag in the current Twin Reading model.

Each response must keep relevant multi-domain membership. This five-case scope demonstrates R1/R2/R3 requests plus alert/blocked outcomes across the five domains. A successful positive water fixture does not establish live preview support. Record that distinction in the handover.

## Test-only policy configuration

Per-domain config lives in config/scenarios/<domain>.json and is owned by that scenario's member. Numeric examples are fixture thresholds, not approved physical safety settings. Power thresholds remain null/disabled until supplied explicitly. Production safety limits, scores, caps, tokens, node IDs and action choices come from shared discovery/configuration.

## Case files each owner creates

Keep cases in mocks/cases/<domain>/. Create base_case.json, refusal_case.json and manifest.json. The manifest lists fixture files and their expected outcomes; it is not a second scenario registry.

Common top-level case fields:

~~~json
{
  "scenario_id": "S01",
  "fixture_only": true,
  "assumptions": [],
  "nodes": [],
  "actions": [],
  "batches": [],
  "policy": {},
  "guardian": {},
  "preview": {},
  "ai_plan": {"proposals": [], "alerts": []},
  "twin_outcome": {},
  "expected": {}
}
~~~

This is a field guide, not a completed runnable case. Each owner fills values matching contracts.py and the partner/action schemas frozen by Elyes. Shared FixtureTwin/FixtureGuardian/FixturePlanProvider load the relevant case sections. If an inner peer shape is unavailable, report it; do not invent a live schema. Only fixture values may be made up and must be listed in assumptions.

- nodes: real-shaped Node records, including domains and any shared membership.
- actions: ActionInfo rows with fixture-only allowed params, carriers and caps. Missing preview support is represented explicitly.
- batches: one or more ReadingsBatch objects, distinct ticks for persistence. Stable reading IDs and simulated timestamps.
- policy: the per-scenario development policy copied from its config.
- guardian: expected evidence assessment/approval, with declared fixture-only cut-offs/lifetime. Token format must be frozen by Elyes before shared peer execution tests.
- preview: availability and safe/unsafe fixture answer, supplied topology justification for water.
- ai_plan: recorded schema-valid proposal/alert. No real key/token in a Plan.
- twin_outcome: fixture result profile: committed/rejected/pending, plus refusal detail.
- expected: decision status, action/targets/params/evidence, allowed call order/count and actuator effect count.

Tokens generated by a fake Guardian remain in memory and out of case files/traces. No network is allowed for case replay. Test-only unsigned approvals are not a claim of tamper-proof authentication.

## Test file layout

For each domain: tests/scenarios/<domain>/test_detection.py, test_planning.py, test_workflow.py and helpers.py if needed. A member may define a tiny recorded provider in helpers.py. No global conftest.py or another member's test edits.

Write detection/planning unit tests first without a shared runtime. Later use CONTRACT.md's build_runtime factory with shared fake peers for full workflow checks. Do not duplicate execution/approval logic in a fake local Brain to make a workflow pass.

Each base case and its refusal variations remain the same scenario ID. The acceptance matrix has five scenario rows plus cross-cutting security/reliability checks. More assertions do not mean more agreed scenarios.

## Internal fixture feature mapping

The shared factory accepts the following keys in features. These are CIVIS internal adapter settings, not claims about Guardian's live API. Fixture names are intentionally prefixed fixture_; Elyes maps confirmed live names separately.

| Key | Type and fixture meaning |
| --- | --- |
| enabled_scenario_ids | list of known S01-S05 IDs; a single-case replay enables its own ID, normal service defaults to all five |
| guardian_score_tool | string; fixture_score for fake peer assessment |
| guardian_token_tool | string; fixture_approve for fake exact-action approval |
| preview_tool | string or null; fixture_preview only in explicitly supported fixture profile |
| commit_tool | string or null; fixture_commit only in optional pending profile |

Enabled selection never bypasses common validation, preview, approval or caps. Preview has no implicit safe default. Shared fixtures expose methods through ToolPeer.call_tool; only the common core invokes them.

Elyes freezes these inner fixture fields before peer execution tests: guardian has score, score_scale, thresholds, approve, token_lifetime_ticks and optional refusal_code; preview has available, safe and reason; twin_outcome has status, optional code/details. Values and scale/lifetimes are explicitly test-only. Fake Guardian generates a token in memory bound to the normalized request. No token string belongs in fixture JSON. Full real token format remains a live partner gap.

The parameter manifest uses current Twin ParamInfo keys: name, type, choices, min_value, max_value, unit. Actual current dispatch inputs are unit_type, destination and units. Allowed carriers/choices/bounds are provided in the case, never guessed by the AI.

Water config may include safe_valve_choices, a list of explicitly supported fixture entries with incident_node_id, targets and params. Default is empty. Detector exposes matching entries in Incident.facts.supported_valve_actions; runtime rechecks them against configured topology/manifest before preview and approval. A nearby valve is not automatically safe. No choice means alert/blocked without an invented direction.

Medical Incident.facts carries destination and ambulance_available_by_carrier derived from actual units_free readings at dispatch carriers. Preserve those availability reading IDs as well as the call reading IDs. Units are calls/min for emergency_calls and units for units_free. Unavailable/unknown availability cannot justify dispatch.

PlanningContext.evidence_readings carries trusted-selected original readings, including earlier persistence ticks; current batch stays unchanged. The shared ledger resolves old source IDs. No reconstruction or invented value replaces missing historical evidence.

## Implementation revision, 8 October

The shared factory, peers and MCP tools are implemented. S03/S04 are working; S01/S02/S05 remain assigned to their owners. See HANDOVER.md for actual support and limitations.

Case format additions:

- caps maps every touched domain to a discovered fixture action limit (integer or explicit null). Shared nodes require each domain's limit.
- guardian.thresholds contains reading and each exercised risk tier, all on guardian.score_scale. These numbers are synthetic fixture configuration, never live defaults.
- guardian.scores optionally overrides score by reading ID; claim_overrides is a test fault-injection field.
- twin_outcome.commit_available explicitly advertises fixture_commit. Missing support leaves pending.
- expected.final_statuses is the ordered list of last-batch decision statuses; effects, provider_calls and actuate_calls are optional exact counts. reason_contains optionally checks a refusal explanation.

~~~json
{
  "guardian": {
    "score": 95.0,
    "score_scale": 100.0,
    "thresholds": {"reading": 60.0, "R1": 65.0, "R2": 80.0, "R3": 90.0},
    "approve": true,
    "token_lifetime_ticks": 3
  },
  "preview": {"available": true, "safe": true, "reason": "Declared synthetic preview"},
  "twin_outcome": {"status": "committed"},
  "expected": {"final_statuses": ["committed"], "effects": 1, "provider_calls": 1, "actuate_calls": 1}
}
~~~

Fake Guardian generates unsigned JWS in memory with iss, aud, jti, run_id, iat, exp, action, targets, params, score and score_scale. It is test-only; real token claims/signature verification require confirmation with 9antra/Twin. Tokens never belong in case JSON.

Additional internal features: peer_timeout_seconds, ai_timeout_seconds, ai_max_calls_per_run and guardian_contract_confirmed. Existing five feature keys and frozen factory/signatures are preserved. Decision.peer_details is an additive redacted object that retains cap/refusal detail.

Synthetic-candidate integration tests bypass only the unfinished detector in the test harness. They run the actual shared validation/approval/execution code and must never be cited as S01/S02/S05 acceptance.
